## 📋 밋업 한눈에 보기

발표자는 데이터 엔지니어링 전 과정에 AI 에이전트를 적용한 사례를 공유했다. configuration table만 입력하면 파이프라인을 자동으로 구성하는 수집 에이전트, primary key 위반 등 품질 문제를 자동으로 잡아 소비 계층에서 제외하는 거버넌스 에이전트, 수천 개 파이프라인의 네트워크·타임아웃 이슈를 스스로 감지하고 복구하는 운영 에이전트를 차례로 설명했다. 다음 단계로는 특정 레코드가 왜 대시보드에 반영되지 않았는지 레이어별로 추적해 원인을 짚어주는 lineage 기반 에이전트를 개발 중이라고 밝혔다. Q&A에서는 AI 에이전트 도입의 ROI를 어떻게 판단하는지에 대한 질문이 나왔고, 발표자는 모든 아이디어를 무분별하게 에이전트화하지 말고 비즈니스 케이스를 철저히 검증해야 한다고 답했다.

## 🔑 핵심 요점

- 소스 시스템 설정(configuration table)만으로 파이프라인을 자동 구성하는 ingestion agent를 도입해 수천 개 수동 파이프라인 관리 부담을 줄였다.
- 데이터 품질·거버넌스를 담당하는 agent가 primary key 위반 같은 문제 데이터를 자동 감지해 소비 계층(consumption layer)에서 제외시킨다.
- 이 거버넌스 agent 도입으로 생산성이 약 35% 개선됐다고 발표자는 밝혔다.
- 수천 개 파이프라인의 운영 이슈(타임아웃, 네트워크 오류 등)를 모니터링하고 스스로 복구하는 self-healing agent를 구축했다.
- 다음 단계로 레코드가 어느 레이어에서 왜 끊겼는지 자동으로 추적해 알려주는 lineage 기반 agent를 개발 중이다.
- 발표자는 AI 에이전트 도입 전 반드시 비용 대비 효과(ROI)를 검증한 비즈니스 케이스가 있어야 한다고 강조했다.
- 문서화 agent가 매번 전체 파이프라인을 스캔해 메모리와 비용을 과도하게 소모한 사례처럼, 아이디어 자체보다 효율을 먼저 따져야 한다고 조언했다.

## 🛠 핵심 기술 쉽게 이해하기

### Ingestion Agent (configuration-driven pipeline automation)

소스 시스템의 종류와 연결 정보를 configuration table에 입력만 하면 agent가 알아서 해당 시스템에서 데이터를 가져와 파이프라인을 구성해주는 자동화 방식이다. 개발자가 매번 코드를 짜서 파이프라인을 만들던 방식과 달리 설정값만 바꾸면 된다.

**왜 필요한가** — 조직 내 35개 이상의 서로 다른 소스 시스템에서 수천 개의 파이프라인을 일일이 수동으로 만들고 유지보수하는 것은 비효율적이고 운영팀에 큰 부담이 되기 때문이다.

**발표에서는** — 발표자는 이 agent가 기존의 수동 파이프라인 구축 방식을 대체해 소스 시스템 연동을 설정값 기반으로 전환했다고 설명했다.

### Data Quality/Governance Agent

데이터가 파이프라인을 거치는 동안 primary key 위반이나 참조 무결성 문제 같은 품질 이슈를 자동으로 검사하는 agent다. 문제가 있는 데이터는 오류 테이블에 기록되고 최종 소비 단계에서 자동으로 제외된다.

**왜 필요한가** — 잘못된 데이터가 대시보드나 리포트까지 그대로 흘러가면 비즈니스 의사결정에 오류를 일으키기 때문에, 소비되기 전 단계에서 걸러내야 한다.

**발표에서는** — 발표자는 이 agent 도입으로 생산성이 약 35% 개선됐으며, 모든 품질 검증이 configuration table 기반으로 일관되게 처리되고 있다고 밝혔다.

### Self-healing Operations Agent

수천 개의 실행 중인 파이프라인을 계속 스캔하면서 네트워크 오류, 타임아웃, 과도한 동시 작업 같은 운영 이슈를 자동으로 감지하는 agent다. 문제가 발생하면 일시적으로 해당 작업을 쉬게 하거나 리소스를 재할당해 복구를 시도한다.

**왜 필요한가** — 3,000개가 넘는 파이프라인을 사람이 직접 모니터링하고 대응하는 것은 운영팀에게 '나이트메어'에 가까운 부담이기 때문이다.

**발표에서는** — 발표자는 소스 시스템 접속이 불안정할 때 agent가 자동으로 재시도하고 몇 분 뒤 다시 연결 가능 여부를 확인하는 식으로 동작한다고 예시를 들었다.

### Medallion Architecture (Bronze/Silver/Gold)

데이터를 원본 그대로인 Bronze, 정제된 Silver, 비즈니스에서 바로 쓸 수 있는 Gold 단계로 나누어 관리하는 데이터 레이크 설계 패턴이다.

**왜 필요한가** — 원시 데이터를 바로 분석에 쓰기 어렵기 때문에 단계별로 정제해 신뢰할 수 있는 데이터를 비즈니스 사용자에게 전달하기 위해 사용한다.

**발표에서는** — 발표자는 자신의 조직이 이 구조로 파이프라인을 운영하며, Gold 레이어가 Power BI나 SSRS 같은 BI 도구로 소비되는 최종 데이터라고 설명했다.

### Lineage/System Table Agent (개발 중)

특정 레코드가 Bronze부터 Gold까지 각 레이어를 거치며 어디서, 왜 누락되거나 걸러졌는지를 자동으로 추적해주는 agent다. join, filter 조건, 참조키 불일치 등 원인을 찾아 알려준다.

**왜 필요한가** — 비즈니스 쪽에서 '왜 내 레코드가 대시보드에 안 보이냐'는 문의가 올 때마다 여러 레이어를 사람이 일일이 디버깅하는 데 시간이 많이 걸리기 때문이다.

**발표에서는** — 발표자는 아직 개발 단계이며, 이 agent가 완성되면 반복적인 데이터 누락 문의에 대응하는 시간을 크게 줄일 것으로 기대한다고 밝혔다.

## 🧭 추구 방향과 흐름

- **AI 에이전트 기반 데이터 엔지니어링 자동화** — 데이터 수집, 품질 검증, 운영 모니터링까지 파이프라인의 각 단계를 사람이 아니라 agent가 맡도록 전환하는 흐름이다. 발표 전체가 수집-품질-운영-원인추적 네 단계에 각각 agent를 배치한 사례로 구성되어 있다.
- **ROI 기반의 신중한 AI 도입** — 유행을 따라 아무 아이디어나 agent로 만들지 않고, 비용 대비 효과를 먼저 검증한 비즈니스 케이스가 있을 때만 도입하는 접근이다. 문서화 agent가 매번 전체 파이프라인을 스캔해 비용이 과도하게 든 사례를 반례로 들며 이 원칙을 강조했다.
- **운영 자동화를 통한 self-service 지향** — 수천 개 파이프라인을 운영팀이 수동으로 감시하는 대신 agent가 스스로 이상을 감지하고 복구하도록 만드는 방향이다. 이는 운영 부담을 줄이고 데이터 소비자가 안정적으로 Gold 레이어 데이터를 쓸 수 있게 하는 것을 목표로 한다.

## 🚀 바로 활용하기

1. 파이프라인을 직접 코딩하기 전에 configuration table 기반으로 소스 시스템을 자동 연동하는 구조를 검토해본다.
2. 데이터 품질 규칙(기본키, 참조 무결성 등)을 agent가 자동 검증하도록 체크리스트와 오류 테이블 설계를 만들어본다.
3. AI 에이전트 도입 전 비용 대비 효과를 계산하는 간단한 비즈니스 케이스 템플릿을 작성해본다.
4. Medallion architecture(bronze/silver/gold)를 적용해 자신의 데이터 레이크/웨어하우스 계층을 정리해본다.
