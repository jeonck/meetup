## 오늘의 기술 토픽

> **Policy as Code**

이번 밋업은 정해진 발표 없이 Policy as Code라는 주제를 중심으로 정리한 브리핑이다. 쿠버네티스 환경에서 보안 규칙, 리소스 제약, 규정 준수 기준을 코드로 정의하고 자동으로 강제하는 접근 방식을 다룬다. Kyverno, OPA/Gatekeeper 같은 정책 엔진과 GitOps 도구를 함께 활용해 사람이 매번 수동 검토하지 않아도 정책 위반을 사전에 차단하는 방향을 설명한다. 궁극적으로는 플랫폼 팀이 셀프서비스 환경에서도 안전한 기본값을 강제할 수 있도록 만드는 것이 목표다.

## 🔑 핵심 요점

- Policy as Code는 보안·컴플라이언스 규칙을 코드로 작성해 버전 관리하고 자동 검증하는 방식이다.
- 쿠버네티스에서는 Admission Controller를 통해 리소스가 생성되기 전에 정책 위반 여부를 검사한다.
- Kyverno는 쿠버네티스 네이티브 문법(YAML)으로 정책을 작성할 수 있어 진입 장벽이 낮다.
- OPA(Open Policy Agent)는 Rego라는 전용 언어로 더 범용적이고 세밀한 정책 표현이 가능하다.
- GitOps와 결합하면 정책 변경 이력도 Git으로 추적되어 감사(audit)가 쉬워진다.
- 플랫폼 엔지니어링 관점에서 Policy as Code는 개발자에게 안전한 셀프서비스 환경을 제공하는 핵심 수단이다.
- 정책은 처음부터 강제(enforce) 모드가 아니라 감사(audit) 모드로 도입해 점진적으로 적용하는 것이 안전하다.

## 🛠 핵심 기술 쉽게 이해하기

### Kyverno

Kyverno는 쿠버네티스 전용으로 설계된 정책 엔진으로, 별도의 새로운 언어 없이 익숙한 YAML로 정책을 작성할 수 있다. 리소스 생성·수정 요청을 가로채 규칙에 맞는지 검사하고, 필요하면 값을 자동으로 수정(mutate)하거나 부족한 리소스를 자동 생성(generate)할 수도 있다.

**왜 필요한가** — 쿠버네티스 클러스터에 잘못된 설정이나 보안 취약점이 있는 리소스가 배포되는 것을 사전에 막기 위해 사용한다.

**발표에서는** — 쿠버네티스 사용자에게 진입 장벽이 낮은 정책 엔진의 예시로 다뤄졌다.

### Open Policy Agent (OPA) / Gatekeeper

OPA는 쿠버네티스뿐 아니라 다양한 시스템에 적용 가능한 범용 정책 엔진이며, Rego라는 전용 언어로 정책 로직을 표현한다. Gatekeeper는 OPA를 쿠버네티스 Admission Controller와 연동해주는 프로젝트다.

**왜 필요한가** — 여러 시스템(API 게이트웨이, CI/CD, 쿠버네티스 등)에 걸쳐 일관된 정책을 적용하고 싶을 때 사용한다.

**발표에서는** — Kyverno와 대비되는 좀 더 범용적이고 강력한 대안으로 언급됐다.

### Admission Controller

쿠버네티스 API 서버에 리소스 생성/수정 요청이 들어올 때, 실제로 저장되기 전에 요청을 가로채 검증하거나 변경하는 확장 지점이다. Validating과 Mutating 두 종류가 있다.

**왜 필요한가** — 정책 엔진들이 실제로 정책을 강제할 수 있도록 만들어주는 쿠버네티스의 기반 메커니즘이다.

**발표에서는** — Kyverno와 OPA/Gatekeeper가 동작하는 원리를 설명하기 위한 배경 개념으로 다뤄졌다.

### GitOps (Argo CD)

GitOps는 Git 저장소를 시스템의 단일 진실 공급원(source of truth)으로 삼아 인프라와 애플리케이션 상태를 관리하는 방식이다. Argo CD는 이를 쿠버네티스에서 자동으로 동기화해주는 대표적인 도구다.

**왜 필요한가** — 정책 코드 자체도 Git으로 관리하면 변경 이력 추적과 롤백, 리뷰 프로세스가 쉬워진다.

**발표에서는** — Policy as Code를 실제 운영에 적용할 때 GitOps 파이프라인과 함께 배포하는 흐름의 일부로 언급됐다.

## 🧭 추구 방향과 흐름

- **플랫폼 엔지니어링과 셀프서비스** — 플랫폼 팀이 개발자에게 인프라를 직접 관리하게 맡기는 대신, 정책으로 안전한 기본값과 가드레일을 미리 설정해두는 방향이다. 이렇게 하면 개발자는 자유롭게 리소스를 생성하면서도 보안·컴플라이언스 기준을 자동으로 지키게 된다.
- **Shift-left 보안** — 보안 검증을 배포 이후가 아니라 리소스가 클러스터에 반영되기 전 단계로 앞당기는 흐름이다. Admission Controller 기반 정책 강제가 이 흐름의 대표적인 구현 방식으로 다뤄졌다.
- **정책의 코드화와 감사 가능성** — 정책을 문서가 아닌 코드로 관리해 Git 이력으로 변경을 추적하고, GitOps 파이프라인에 통합해 자동으로 배포·적용하는 방향으로 발전하고 있다.

## 🚀 바로 활용하기

1. 로컬 kind/minikube 클러스터에 Kyverno를 설치하고 공식 예제 정책(예: 필수 라벨 강제)을 적용해본다.
2. Kyverno Policy Library에서 자주 쓰이는 보안 정책 샘플을 살펴보고 하나를 audit 모드로 적용해본다.
3. OPA Rego 언어를 공식 Playground에서 간단한 규칙으로 실습해보며 Kyverno와 문법 차이를 비교한다.
4. Argo CD 공식 문서를 참고해 정책 매니페스트를 Git 저장소로 관리하고 자동 동기화하는 흐름을 구성해본다.
