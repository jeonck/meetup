## 오늘의 기술 토픽

> **Zero Trust Networking**

이 글은 특정 밋업 발표가 아니라 Zero Trust Networking이라는 주제를 처음 접하는 개발자를 위해 정리한 기술 브리프다. 전통적인 경계 기반 보안(perimeter security)이 클라우드 네이티브 환경에서 한계를 드러내면서, 네트워크 내부 통신도 기본적으로 신뢰하지 않고 매 요청마다 신원을 검증하는 Zero Trust 모델이 주목받고 있다. Kubernetes와 서비스 메시, eBPF 기반 네트워킹 도구들이 이 모델을 실제로 구현하는 핵심 축으로 쓰인다. 이 브리프는 관련 기술 개요와 학습 방향, 실천 항목을 정리한 것이다.」

## 🔑 핵심 요점

- Zero Trust Networking은 '내부 네트워크는 안전하다'는 전제를 버리고 모든 통신을 매번 인증·인가하는 보안 모델이다.
- 전통적인 방화벽/VPN 중심의 경계 보안은 마이크로서비스와 멀티클라우드 환경에서 더 이상 충분하지 않다.
- mTLS(상호 TLS)는 서비스 간 통신을 암호화하고 양쪽의 신원을 확인하는 Zero Trust 구현의 핵심 수단이다.
- SPIFFE/SPIRE 같은 워크로드 아이덴티티 표준은 서비스가 누구인지 증명하는 공통 언어 역할을 한다.
- Cilium 같은 eBPF 기반 네트워킹 도구는 커널 레벨에서 세밀한 네트워크 정책을 강제할 수 있게 해준다.
- Zero Trust는 한 번에 도입하는 제품이 아니라 아이덴티티, 정책, 관측성을 아우르는 지속적인 아키텍처 전환 과정이다.

## 🛠 핵심 기술 쉽게 이해하기

### Zero Trust Networking

네트워크 위치(내부망인지 외부망인지)와 무관하게 모든 접근 요청을 매번 검증하는 보안 모델이다. '한 번 인증되면 계속 신뢰'하는 대신 '항상 검증'을 원칙으로 삼는다.

**왜 필요한가** — 마이크로서비스, 클라우드, 원격 근무 환경에서는 고정된 네트워크 경계가 사라지기 때문에, 경계 방어만으로는 내부 침투나 측면 이동(lateral movement) 공격을 막기 어렵다.

**발표에서는** — 이 브리프에서는 개별 발표 내용이 아니라, Zero Trust가 왜 클라우드 네이티브 보안의 기본 전제로 자리잡고 있는지 배경 개념으로 소개한다.

### mTLS (Mutual TLS)

일반 TLS가 서버 신원만 확인하는 것과 달리, 클라이언트와 서버 양쪽이 서로의 인증서를 검증하는 방식이다. 서비스 간 통신을 암호화하면서 동시에 '누가 요청했는지'까지 증명한다.

**왜 필요한가** — 서비스 메시 내부의 파드 간 통신도 도청이나 위조 위험에서 자유롭지 않기 때문에, Zero Trust를 실제로 구현하려면 통신 구간 자체를 암호화하고 상호 인증해야 한다.

**발표에서는** — Istio, Linkerd 같은 서비스 메시가 mTLS를 기본 기능으로 제공하며 Zero Trust 도입의 출발점으로 자주 언급되는 기술로 소개한다.

### SPIFFE / SPIRE

SPIFFE(Secure Production Identity Framework For Everyone)는 워크로드에 표준화된 신원(SPIFFE ID)을 부여하는 사양이고, SPIRE는 이를 실제로 발급·검증하는 구현체다. 플랫폼이나 클라우드에 상관없이 동일한 방식으로 서비스 신원을 증명할 수 있다.

**왜 필요한가** — 서로 다른 클러스터, 클라우드, VM에 흩어진 워크로드가 서로를 신뢰할 수 있는 공통된 신원 체계가 없으면 Zero Trust 정책을 일관되게 적용하기 어렵다.

**발표에서는** — 여러 서비스 메시와 플랫폼 도구들이 SPIFFE를 워크로드 아이덴티티의 표준 기반으로 채택하고 있는 흐름을 설명하는 예시로 다룬다.

### Cilium

eBPF 기술을 기반으로 Kubernetes 네트워킹과 네트워크 정책, 관측성을 제공하는 CNI(Container Network Interface) 플러그인이다. 리눅스 커널 레벨에서 트래픽을 처리해 기존 iptables 기반 방식보다 빠르고 세밀한 제어가 가능하다.

**왜 필요한가** — L3/L4뿐 아니라 L7(HTTP, gRPC 등) 수준까지 세밀한 정책을 커널 단에서 적용할 수 있어야 파드 단위, API 단위로 Zero Trust 정책을 강제할 수 있다.

**발표에서는** — eBPF 기반 도구가 서비스 메시 없이도 네트워크 정책과 신원 기반 접근 제어를 가능하게 해주는 최신 접근법으로 소개한다.

## 🧭 추구 방향과 흐름

- **경계 보안에서 아이덴티티 기반 보안으로** — IP나 네트워크 위치가 아니라 워크로드/사용자의 신원(identity)을 기준으로 접근을 통제하는 방향으로 이동하고 있다. SPIFFE/SPIRE 같은 표준화된 아이덴티티 프레임워크가 이 흐름의 핵심 인프라로 자리잡고 있다.
- **서비스 메시와 eBPF의 역할 분담 및 통합** — Istio 같은 서비스 메시는 L7 정책과 mTLS를, Cilium 같은 eBPF 기반 CNI는 커널 레벨의 고성능 네트워킹과 관측성을 담당하며 서로 보완적으로 결합되는 방향으로 발전하고 있다.
- **정책 코드화(Policy as Code)** — 네트워크 정책과 접근 제어 규칙을 YAML이나 코드로 선언하고 GitOps 방식으로 관리하는 흐름이 확산되고 있어, Zero Trust 정책 역시 코드로 관리하고 버전 관리하는 것이 표준으로 자리잡고 있다.
- **지속적 검증과 관측성 결합** — 한 번의 인증으로 끝나는 것이 아니라 지속적으로 트래픽을 관측하고 이상 징후를 탐지하는 것이 Zero Trust의 실질적 완성도를 높이는 방향으로 강조되고 있다.

## 🚀 바로 활용하기

1. 로컬에 kind나 minikube로 Kubernetes 클러스터를 만들고 Cilium을 CNI로 설치해 NetworkPolicy를 적용해본다.
2. Istio 공식 문서의 Getting Started를 따라 데모 앱에 mTLS를 활성화하고 mTLS 강제(STRICT) 모드를 테스트해본다.
3. SPIFFE/SPIRE 공식 Quickstart로 워크로드에 SPIFFE ID를 발급하고 검증하는 과정을 직접 실습해본다.
4. CNCF의 Zero Trust 관련 백서나 프로젝트 목록을 훑어보며 관련 생태계 지도를 그려본다.
