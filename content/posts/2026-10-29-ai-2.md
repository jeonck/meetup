## 📋 밋업 한눈에 보기

두 발표자는 광고/세금 데이터 생태계와 IoT 디바이스 운영 경험을 바탕으로 AI를 인프라 최적화에 적용할 때의 실전 교훈을 공유했다. AI를 만능 해결책(실버불릿)이나 블랙박스로 취급하지 말고 human-in-the-loop를 유지하며 모델 결과를 지속적으로 평가해야 한다고 강조했다. 특히 AI 도입 비용과 실제 비즈니스 운영비 절감 효과를 비교해 투자 타당성을 따져야 하며, 신규 기능 개발인지 기존 시스템 최적화인지에 따라 다른 모델을 선택하는 전략이 필요하다고 설명했다. 저렴한 월 구독료로 운영되는 IoT 서비스처럼 마진이 낮은 사업에서는 인프라 비용 효율이 수익성에 직결된다는 점도 다뤄졌다.

## 🔑 핵심 요점

- AI를 '실버불릿'처럼 모든 문제를 해결하는 만능 도구로 보지 말고, human-in-the-loop를 유지하며 신뢰성을 검증해야 한다.
- AI는 블랙박스가 아니라 지속적으로 평가하고 비교해야 하는 대상이며, 어떤 모델이 어떤 비즈니스에 더 적합한지 꾸준히 확인해야 한다.
- AI 도입 비용과 그로 인해 줄어드는 비즈니스 운영 비용을 비교해, 순효과가 긍정적일 때만 투자를 지속해야 한다.
- 모든 작업에 가장 크고 비싼 모델을 쓸 필요는 없다. 내부 도구에는 저비용 모델, 배포/테스트처럼 품질과 SLA가 중요한 작업에는 더 신중하게 모델을 선택해야 한다.
- 신규 기능 개발과 기존 시스템 최적화/버그 수정은 성격이 다른 작업이므로 AI 에이전트 활용 전략도 다르게 설계해야 한다.
- IoT처럼 디바이스당 마진이 매우 낮은 사업에서는 사용량이 10%만 달라져도 수익에 큰 영향을 주므로 자가 최적화 인프라가 중요하다.
- 매출이 분 단위로 줄어드는 비즈니스 크리티컬 서비스에는 더 엄격한 AI 평가와 모니터링이 필요하다.

## 🛠 핵심 기술 쉽게 이해하기

### AI Agents / LLM 기반 자동화

대규모 언어 모델을 활용해 반복적인 데이터 분석, 모니터링, 의사결정 업무를 자동화하는 기술이다. 사람이 직접 하던 운영 작업을 모델이 대신 처리하도록 만든다.

**왜 필요한가** — 방대한 데이터(광고/세금 데이터, IoT 센서 데이터 등)를 빠르게 처리해 시장에서 먼저 움직이기 위해 도입한다.

**발표에서는** — 발표자는 AI 도입 이후 많은 반복 업무가 자동화되었다고 소개하면서도, 이를 무조건적인 해결책으로 보면 안 된다고 경고했다.

### Human-in-the-loop (HITL)

AI가 내놓은 결과를 사람이 검토하고 개입할 수 있도록 설계하는 운영 방식이다. AI의 판단을 그대로 자동 적용하지 않고 중요한 지점에서 사람이 확인하는 체계를 말한다.

**왜 필요한가** — AI가 환각(hallucination)을 일으키거나 체크 로직을 우회하는 경우가 있어, 특히 비즈니스에 중요한 결정에서는 사람의 검증이 필요하다.

**발표에서는** — 발표자는 AI 결과를 그대로 신뢰하면 체크 로직도 우회될 수 있다는 사례를 들며 human-in-the-loop를 유지해야 한다고 강조했다.

### 멀티 모델 전략 / 모델 라우팅

하나의 거대 모델만 쓰는 대신, 작업 성격에 맞춰 여러 종류의 AI 모델을 선택적으로 사용하는 전략이다.

**왜 필요한가** — 모든 작업에 가장 비싸고 강력한 모델을 쓰면 비용이 과도해지므로, 품질 요구 수준과 SLA에 맞는 모델을 골라 비용을 최적화한다.

**발표에서는** — Q&A에서 발표자는 신규 기능 개발에는 품질이 중요한 모델을, 내부 도구나 배포/테스트처럼 덜 민감한 작업에는 저비용 모델을 쓴다고 답했다.

### IoT 디바이스 / 엣지 인프라

센서나 커넥티드 기기에서 대량의 데이터를 지속적으로 전송하는 환경을 가리킨다. 디바이스 자체는 저가이지만 운영 비용 구조가 중요한 영역이다.

**왜 필요한가** — 월 구독료가 낮은 서비스에서는 디바이스/인프라 효율이 조금만 떨어져도 전체 수익성에 큰 타격을 줄 수 있어 비용 효율이 핵심 과제가 된다.

**발표에서는** — 두 번째 발표자는 대규모 IoT 디바이스를 다루는 경험을 바탕으로, 사용량 차이가 10%만 나도 비용에 큰 영향을 준다고 설명했다.

### MTTR (Mean Time To Repair) 모니터링

장애나 문제가 발생했을 때 이를 복구하는 데 걸리는 평균 시간을 측정하는 신뢰성 지표다.

**왜 필요한가** — 복구 속도를 수치화해야 고객에게 영향을 주는 문제를 더 빠르게 식별하고 개선할 수 있다.

**발표에서는** — 발표자는 MTTR 개선을 통해 복구 효율성을 높이고 고객에게 미치는 영향을 줄이려는 시도를 언급했다.

## 🧭 추구 방향과 흐름

- **AI를 실버불릿이 아닌 비용 대비 효과로 판단하기** — 발표자들은 AI가 모든 문제를 해결해주는 만능 도구가 아니라, 도입 비용과 그로 인한 운영비 절감 효과를 비교해서 투자 타당성을 판단해야 하는 대상이라고 반복해서 강조했다. 'AI는 블랙박스가 아니다'라는 발언이 이 방향을 잘 보여준다.
- **작업 유형별 모델 선택(모델 라우팅)** — 신규 기능 개발, 내부 도구, 배포/테스트처럼 요구되는 품질과 SLA가 다른 작업에는 각각 다른 모델을 쓰는 전략이 필요하다는 방향을 제시했다. Q&A에서 이 부분이 구체적으로 다뤄졌다.
- **Human-in-the-loop 유지** — AI가 환각을 일으키거나 체크 로직을 우회하는 사례들이 있기 때문에, 완전 자동화보다는 사람이 중요한 지점에서 개입할 수 있는 체계를 유지하는 방향으로 가야 한다고 설명했다.
- **자가 최적화 인프라와 지속적 모니터링** — 대규모 디바이스를 운영하는 환경에서는 사용량, 복구 시간(MTTR) 등을 지속적으로 측정하고 자동으로 최적화하는 인프라를 구축하는 것이 핵심 과제로 제시됐다.

## 🚀 바로 활용하기

1. AI 도입 전, 도입 비용과 그로 인해 절감되는 운영 비용을 비교하는 간단한 ROI 계산표를 만들어보자.
2. 신규 기능 개발용, 내부 도구용, 배포/테스트용 작업을 구분하고 각각에 어떤 등급의 모델을 쓸지 정리해보자.
3. AI가 자동으로 처리하는 중요 로직에 human-in-the-loop 체크포인트를 하나 이상 추가해보자.
4. 서비스에 MTTR 같은 복구 시간 지표를 도입해 장애 대응 속도를 측정해보자.
