## 오늘의 기술 토픽

> **eBPF Networking**

eBPF는 커널을 재컴파일하거나 커널 모듈을 새로 만들지 않고도 리눅스 커널 내부 동작을 안전하게 확장할 수 있게 해주는 기술로, 최근 클라우드 네이티브 네트워킹과 보안 영역에서 핵심 인프라로 자리잡고 있습니다. Cilium 같은 CNI가 eBPF를 기반으로 커널 레벨에서 패킷 처리를 수행하면서 기존 iptables 기반 네트워킹보다 훨씬 빠르고 관측 가능한 구조를 제공합니다. 여기에 Hubble 같은 관측 도구와 Cilium Service Mesh가 결합되면서, 별도의 사이드카 프록시 없이도 서비스 메시 기능을 구현하려는 흐름이 확산되고 있습니다. 오늘 정리한 내용은 eBPF 네트워킹을 처음 접하는 개발자가 어떤 기술들을 함께 살펴봐야 하는지에 초점을 맞춘 기술 브리프입니다.

## 🔑 핵심 요점

- eBPF는 커널 소스를 수정하거나 커널 모듈을 로드하지 않고도 커널 내부에서 프로그램을 안전하게 실행할 수 있게 해주는 기술이다.
- 네트워킹 영역에서 eBPF는 패킷을 커널 초기 단계에서 처리해 기존 iptables 방식보다 오버헤드가 적다.
- Cilium은 eBPF를 기반으로 만들어진 대표적인 Kubernetes CNI로, 네트워킹·보안·관측을 하나로 통합한다.
- Cilium의 Hubble은 eBPF로 수집한 트래픽 데이터를 시각화해 클러스터 내부 통신을 실시간으로 들여다볼 수 있게 해준다.
- eBPF 기반 서비스 메시는 사이드카 프록시 없이 동작할 수 있어 리소스 오버헤드와 운영 복잡도를 줄이는 방향으로 발전 중이다.
- eBPF는 네트워킹뿐 아니라 보안 정책 적용, 성능 프로파일링 등 커널 레벨 관측·제어가 필요한 다양한 영역으로 응용 범위가 넓어지고 있다.

## 🛠 핵심 기술 쉽게 이해하기

### eBPF

eBPF(extended Berkeley Packet Filter)는 리눅스 커널 안에서 샌드박스화된 프로그램을 실행할 수 있게 해주는 기술입니다. 커널 소스 코드를 고치거나 별도의 커널 모듈을 만들지 않고도, 검증된 작은 프로그램을 커널의 특정 지점(훅)에 붙여 동작을 확장할 수 있습니다.

**왜 필요한가** — 커널을 직접 수정하지 않고도 네트워킹, 보안, 관측 같은 저수준 기능을 안전하고 빠르게 확장하기 위해 사용합니다.

**발표에서는** — eBPF 네트워킹이라는 주제 자체가 이 기술을 중심으로 다뤄지며, 다른 기술들의 기반 개념으로 소개됩니다.

### Cilium

Cilium은 eBPF를 기반으로 만들어진 Kubernetes용 CNI(컨테이너 네트워크 인터페이스)입니다. 파드 간 네트워킹, 네트워크 정책 기반 보안, 로드밸런싱 기능을 커널 레벨에서 처리합니다.

**왜 필요한가** — 기존 iptables 기반 네트워킹의 성능 한계와 복잡한 규칙 관리를 개선하고, 네트워킹과 보안을 하나의 계층에서 통합 관리하기 위해 사용합니다.

**발표에서는** — eBPF 네트워킹의 대표 구현체로 언급되며, 클러스터 네트워킹을 실제로 어떻게 개선하는지 보여주는 사례로 다뤄집니다.

### Hubble

Hubble은 Cilium과 함께 제공되는 네트워크 관측 도구로, eBPF가 수집한 트래픽 데이터를 기반으로 서비스 간 통신을 시각화합니다.

**왜 필요한가** — 클러스터 내부에서 어떤 서비스가 어떤 서비스와 통신하는지, 어디서 트래픽이 막히는지를 빠르게 파악하기 위해 사용합니다.

**발표에서는** — Cilium이 제공하는 관측 기능의 예시로 함께 언급됩니다.

### Cilium Service Mesh

Cilium Service Mesh는 별도의 사이드카 프록시 없이 eBPF와 커널 레벨 기능만으로 서비스 메시 기능(트래픽 제어, mTLS, 관측 등)을 구현하려는 접근 방식입니다.

**왜 필요한가** — Istio 같은 기존 사이드카 기반 서비스 메시의 리소스 오버헤드와 운영 복잡성을 줄이기 위해 등장했습니다.

**발표에서는** — eBPF 기반 네트워킹이 서비스 메시 영역까지 확장되는 흐름의 예시로 소개됩니다.

## 🧭 추구 방향과 흐름

- **사이드카 없는 서비스 메시로의 전환** — 기존 서비스 메시는 파드마다 사이드카 프록시를 붙여 트래픽을 제어했지만, 리소스 오버헤드와 운영 복잡도가 크다는 한계가 있었습니다. eBPF 기반 네트워킹은 커널 레벨에서 직접 트래픽을 처리함으로써 사이드카 없이도 유사한 기능을 제공하려는 방향으로 나아가고 있습니다.
- **커널 레벨 관측 가능성 확대** — Hubble처럼 eBPF 데이터를 활용한 관측 도구가 늘어나면서, 애플리케이션 코드를 수정하지 않고도 네트워크 트래픽과 시스템 동작을 깊이 있게 들여다볼 수 있는 방향으로 관측 생태계가 발전하고 있습니다.
- **네트워킹과 보안의 통합** — Cilium처럼 네트워킹 계층에서 정책 기반 보안까지 함께 처리하는 구조가 늘면서, 별도의 보안 계층을 추가하기보다 네트워킹 인프라 자체에 보안 기능을 내재화하려는 흐름이 나타나고 있습니다.

## 🚀 바로 활용하기

1. 로컬 환경에 minikube나 kind로 Kubernetes 클러스터를 만들고 Cilium을 CNI로 설치해본다.
2. Cilium 공식 문서의 Getting Started 가이드를 따라 Hubble UI로 클러스터 내 트래픽을 시각화해본다.
3. eBPF 공식 사이트에서 eBPF의 기본 개념(훅, 맵, 검증기)을 다루는 입문 문서를 읽어본다.
4. Cilium Service Mesh 문서를 읽고 기존에 써본 사이드카 기반 서비스 메시(예: Istio)와 구조적 차이를 비교해본다.
