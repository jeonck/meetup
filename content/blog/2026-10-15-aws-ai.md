## 왜 지금 멀티 계정인가
많은 조직이 AWS 계정 하나로 시작하지만, 보안을 체계적으로 관리하려면 결국 AWS Organizations 기반의 멀티 계정 구조로 넘어가게 된다. AWS의 [Control Tower 랜딩존 설계 가이드](https://docs.aws.amazon.com/prescriptive-guidance/latest/designing-control-tower-landing-zone/introduction.html)는 계정 구조, 로깅, 인증 등을 사전에 설계 문서로 정리할 것을 권장하며, 워크로드를 관리(management) 계정에 두지 말고 로그 아카이빙, 보안 도구, 샌드박스용으로 별도 계정을 분리하라는 원칙을 제시한다. 핵심은 '한 번에 전부 이전'이 아니라, Control Tower로 랜딩존을 먼저 세운 뒤 신규 워크로드부터 점진적으로 새 계정으로 옮기고 기존 계정은 서서히 하나의 워크로드 계정으로 수렴시키는 단계적 접근이다.

## 탐지에서 대응까지, 자동화의 성숙도
Amazon GuardDuty와 AWS Security Hub(현재 'Security Hub CSPM')를 EventBridge, Lambda, SSM Automation과 엮으면 탐지부터 격리까지 수 초 안에 처리할 수 있다. Security Hub는 ASFF(AWS Security Finding Format)로 정규화된 findings를 [EventBridge로 실시간 전달](https://aws.amazon.com/blogs/security/correlate-security-findings-with-aws-security-hub-and-amazon-eventbridge)하며, 완전 자동 대응은 EventBridge 규칙으로, 사람이 승인 버튼을 눌러야 하는 반자동 대응은 custom action으로 구현하는 두 트랙을 [공식 가이드](https://docs.aws.amazon.com/securityhub/latest/userguide/automations.html)에서 제공한다. AWS의 [보안 운영 성숙도 로드맵](https://aws.amazon.com/blogs/security/operationalizing-aws-security-a-maturity-roadmap)은 '알림 분류 → 티어별 라우팅(치명적 15분, 높음 4시간 이내) → 고신뢰·가역적 조치에 한해 자동화 → 지표 기반 재검토'로 이어지는 단계를 제시하는데, 이는 '되돌릴 수 있는 조치만 자동화하고, 증거(스냅샷)부터 보존하라'는 실무 원칙과 정확히 일치한다. 비용 정당화는 [GuardDuty의 30일 무료 체험과 콘솔 비용 추정 기능](https://docs.aws.amazon.com/guardduty/latest/ug/monitoring_costs.html)으로 실사용 기반 예측치를 뽑고, 이를 로그 파이프라인·상관분석·대응 인력을 직접 구축하는 비용 및 체류시간(dwell time) 단축 효과와 비교하는 방식이 현실적이다.

## VPN에서 제로 트러스트로
제로 트러스트의 이론적 기반인 [NIST SP 800-207](https://csrc.nist.gov/pubs/sp/800/207/a/final)은 네트워크 위치만으로 암묵적 신뢰를 부여하지 않으며, 모든 요청 이전에 주체와 기기를 인증·인가해야 한다는 원칙을 명시한다. AWS Verified Access는 이를 구현한 서비스로, VPN처럼 사용자를 특정 서브넷에 '배치'하는 대신 요청마다 ID와 기기 상태를 평가해 접근을 허용한다([AWS 발표](https://www.networkworld.com/article/3695174/aws-secures-access-to-cloud-apps-without-using-vpns.html)). 다만 레거시 프로토콜이나 관리자 접근처럼 당장 전환이 어려운 영역은 [AWS Client VPN과 공존·마이그레이션 패턴](https://aws.amazon.com/blogs/networking-and-content-delivery/aws-client-vpn-and-aws-verified-access-migration-and-interoperability-patterns)을 따라 단계적으로 옮기면 된다. 제로 트러스트는 '한 번에 끝내는 프로젝트'가 아니라 네트워크 의존도를 지속적으로 줄여가는 여정이라는 점이 핵심이다.

## 생성형 AI 에이전트 시대의 새 경계
AI 에이전트가 도구를 호출하고 데이터를 다루기 시작하면서 보안 경계도 바뀌고 있다. AWS는 [프롬프트 인젝션 대응 가이드](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-injection.html)에서 에이전트에 guardrail을 연결하고 전처리 단계에서 입력 안전성을 모델로 검증할 것을 권고하며, 2026년 6월에는 [AgentCore Policy에 Bedrock Guardrails를 통합](https://aws.amazon.com/it/about-aws/whats-new/2026/06/amazon-bedrock-agentcore-policy-guardrails-generally-available/)해 게이트웨이 단에서 Cedar 기반 default-deny 정책으로 도구 호출을 통제하는 레이어를 추가했다. 동시에 [AgentCore 런타임 보안 모범 사례](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html)는 에이전트 실행 역할의 권한이 호출 주체보다 많아서는 안 된다는 최소 권한 원칙과 IAM Access Analyzer 활용을 강조한다. 즉, 콘텐츠 필터링(guardrail)과 접근 제어(IAM 최소 권한)는 서로 대체 관계가 아니라 함께 설계해야 하는 별개의 통제다. 사람 승인이 필요한 고위험 도구 실행, 모든 모델 호출의 로깅, 프롬프트 인젝션·과도한 자율성(excessive agency)을 포함한 위협 모델링은 이제 AI 애플리케이션 보안의 기본 체크리스트가 되고 있다.

## 도입을 위한 제언
네 가지 흐름은 결국 하나의 메시지로 수렴한다. 보안을 '한 번에 완성하는 상태'가 아니라 '단계적으로 성숙시키는 과정'으로 설계하라는 것이다. 랜딩존부터 세우고 점진적으로 계정을 늘리고, 알림-승인-자동화 순으로 대응 체계를 성숙시키고, VPN 의존을 조금씩 줄여 제로 트러스트로 이행하고, 에이전트에는 처음부터 최소 권한과 guardrail을 함께 적용하는 것. 이것이 현재 AWS 생태계가 권장하는 실질적인 로드맵이다.
